# AI Recorder 3.0 迭代规划

> 基于 `优化建议/20260523-01.txt`、当前源码和既有文档复核。结论：建议总体有效，但需要把优先级从“技术优化清单”重排为“日常可放心使用”的产品路线。

## 1. 建议有效性复核

### 高度有效，应进入 3.0 主线

| 建议 | 结论 | 依据 |
| --- | --- | --- |
| 任务状态恢复 | 有效，P0 | 当前转写和摘要使用 FastAPI `BackgroundTasks` 触发；进程重启后后台任务会丢失，`startup` 只初始化数据库和启动 watcher，没有恢复 running 任务。 |
| LLM 重试和超时 | 有效，P0 | 摘要调用直接使用 OpenAI client，缺少统一重试策略；网络抖动会直接让任务失败。 |
| ASR 并发控制 | 有效，P0 | 配置中有 `asr_max_concurrency`，但 ASR 执行路径没有使用该配置；多次触发转写可能并发跑 CPU 密集任务。 |
| ffmpeg 超时 | 有效，P0 | `subprocess.run()` 没有 `timeout`，损坏音频或异常进程可能长时间卡住。 |
| 音频播放器 + 转写时间轴联动 | 有效，P0 | 详情面板展示转写片段和时间戳，但没有 `<audio>` 播放器，也不能点击转写跳转播放位置。 |
| 转写文本编辑 | 有效，P0/P1 | ASR 结果不是最终可信文本，实际使用中必须允许校对保存。 |
| 内容搜索与标签 | 有效，P1 | 当前列表搜索只按文件名过滤；录音库增长后查找困难。 |
| 批量操作 | 有效，P1 | 当前只能单条转写、摘要、删除，不适合整理大量录音。 |
| 结构化日志 | 有效，P1 | 删除文件和部分异常处理存在静默吞错，排查长期运行问题困难。 |
| 测试覆盖 | 有效，P1 | 当前源码目录没有项目自有测试文件，后续改任务系统和编辑能力时风险会明显上升。 |

### 部分有效，需要调整优先级或方案

| 建议 | 调整 |
| --- | --- |
| WebSocket 替代轮询 | 方向正确，但 3.0 不必先做。当前 1.5 秒轮询可接受，先把任务状态持久化、重试、取消做好；实时推送放到 3.1。 |
| App.tsx 拆 Hook / Context | 有效，但应服务于具体功能切片。先抽 `useRecordings`、`useActiveTask`、`useSettings`，不做纯架构大搬家。 |
| Tailwind / shadcn | 暂不进入 3.0 主线。当前 CSS 已能支撑产品，改 UI 栈会扩大风险，等核心交互稳定后再评估。 |
| 路由库 | 有价值，但低于音频播放、编辑、任务可靠性。3.0 可先实现 URL 查询参数保留选中录音，完整路由放后续。 |
| Alembic | 长期需要，但当前手写 SQLite 增量迁移仍可维护。3.0 可以先增加 schema version 表和迁移测试，暂不强制引入 Alembic。 |
| 说话人分离 | 有产品价值，但 CPU 成本高。3.0 只做数据结构和 UI 兼容，真正 diarization 作为实验开关。 |

### 不准确或已过时

| 建议 | 复核结论 |
| --- | --- |
| “缺少 models 定义文件” | 不准确。当前已有 `backend/app/models/recording.py`、`summary.py`、`task.py`、`transcript.py`、`watch_event.py`。 |
| “无删除/导出能力” | 已过时。当前已有录音删除、摘要删除、转写/摘要 MD 和 TXT 导出。 |
| “设置后 SummaryService 一定不刷新” | 风险描述需要细化。设置 API 会 `get_settings.cache_clear()`，且任务中每次 `SummaryService()` 会重新实例化；真正问题是运行中的任务不会感知中途改配置，以及 OpenAI client 缺少 timeout/retry。 |
| “温度值没有限制” | 已过时。后端 Pydantic 已限制 temperature/top_p 范围；前端仍可增加输入层校验。 |

## 2. 3.0 产品目标

3.0 的目标不是“功能堆满”，而是把 AI Recorder 从可跑 MVP 推到可日常依赖的本地工作台：

1. 任务可靠：重启、失败、误点、网络波动都能被看见、可恢复、可重试、可取消。
2. 内容可校对：能听音频、看时间轴、改转写、保留人工修订。
3. 资料可管理：大量录音能搜索、筛选、打标签、批量处理。
4. 输出可交付：导出格式覆盖 Markdown、TXT、JSON、SRT、DOCX。
5. 维护可验证：关键链路有日志、健康检查和最小测试集。

## 3. 版本边界

### 3.0 必做

- 任务恢复、重试、取消、并发限制。
- ffmpeg / LLM timeout。
- 音频播放和转写时间轴联动。
- 转写片段编辑保存。
- 内容搜索、标签、批量操作。
- 结构化日志和最小测试集。

### 3.0 不做或只预留

- 不切换 Tailwind / shadcn。
- 不把后台任务拆成 Celery/Redis。
- 不默认开启说话人分离。
- 不做完整多用户账号系统。
- 不做全链路离线 LLM。

## 4. 实施路线

### Phase 0：可靠性地基

#### Task 1：任务状态恢复

**说明：** 启动时扫描 `queued` / `running` / `normalizing` / `transcribing` 等未完成任务，按更新时间和类型标记为可重试或失败，避免重启后永久卡住。

**验收标准：**
- 后端启动后不会保留无执行者的 running 任务。
- 录音详情能显示“上次任务中断，可重试”。
- 用户可对中断任务一键重试。

**验证：**
- 构造 running 任务后重启后端，任务被恢复为 `interrupted` 或 `error`。
- 原有已完成任务不受影响。

**依赖：** 无。

**预计范围：** 中。

#### Task 2：任务执行锁和 ASR 并发限制

**说明：** 使用进程内任务队列或全局执行器，实际应用 `ASR_MAX_CONCURRENCY`，同一录音避免重复提交同类任务。

**验收标准：**
- 同时点击多条转写时，最多只运行配置数量的 ASR 任务。
- 超额任务保持 queued，并在前一个任务结束后继续。
- 同一录音重复点击转写不会创建多个并发任务。

**验证：**
- 用 mock ASR 执行器提交多任务，确认并发数不超过配置。
- 前端能显示 queued / running / completed。

**依赖：** Task 1。

**预计范围：** 中。

#### Task 3：超时、重试和取消

**说明：** 为 ffmpeg、LLM 请求和任务流程增加 timeout；摘要的网络类失败自动重试；任务表增加取消标记，前端提供取消按钮。

**验收标准：**
- ffmpeg 卡住时按配置超时失败，并记录错误。
- LLM 摘要网络失败最多重试 2-3 次。
- 用户取消后任务停止后续阶段，状态为 cancelled。

**验证：**
- mock ffmpeg 超时、mock LLM 502、手动取消任务。

**依赖：** Task 2。

**预计范围：** 中。

### Checkpoint A：可靠性验收

- `check.ps1` 正常。
- 后端任务相关单元测试通过。
- 手动验证：提交转写、取消、重试、重启恢复。

### Phase 1：播放和校对

#### Task 4：安全音频播放接口

**说明：** 后端提供受控的录音音频读取接口，支持 HTTP Range，前端详情面板嵌入播放器。

**验收标准：**
- 用户可在详情页播放原始音频。
- 大文件播放不一次性读入内存。
- 接口只允许读取已入库录音路径，不允许任意文件路径读取。

**验证：**
- 播放 mp3 / wav / m4a 样例。
- 尝试不存在录音返回 404。
- 尝试路径穿越不可访问。

**依赖：** 无，可与 Phase 0 并行。

**预计范围：** 中。

#### Task 5：转写时间轴联动

**说明：** 点击转写片段时跳转播放器时间；播放时高亮当前片段。

**验收标准：**
- 点击 `[00:12 - 00:18]` 片段后音频跳到 12 秒。
- 播放过程中当前片段高亮。
- 无时间戳片段正常显示，不破坏页面。

**验证：**
- 用已有 `start_time` / `end_time` 片段手动播放验证。

**依赖：** Task 4。

**预计范围：** 中。

#### Task 6：转写编辑和保存

**说明：** 支持逐段编辑转写文本，保存到数据库和 JSON 文件，并记录更新时间。

**验收标准：**
- 用户能编辑单个片段文本并保存。
- 保存后刷新页面仍保留修改。
- 重新生成摘要使用编辑后的转写文本。

**验证：**
- 编辑片段、刷新、导出、生成摘要。

**依赖：** Task 5。

**预计范围：** 中。

### Checkpoint B：校对体验验收

- 选中录音后可播放、跳转、高亮、编辑、保存。
- 导出内容与编辑后文本一致。

### Phase 2：录音库管理

#### Task 7：全文搜索

**说明：** 后端提供搜索 API，支持文件名、转写文本、摘要内容检索；前端搜索框可选择范围。

**验收标准：**
- 搜关键词能命中文件名、转写片段、摘要内容。
- 搜索结果显示命中位置摘要。
- 无关键词时保留当前列表行为。

**验证：**
- 构造三类命中数据，搜索结果准确。

**依赖：** Task 6。

**预计范围：** 中。

#### Task 8：标签管理

**说明：** 为录音增加标签编辑和筛选能力，支持常用标签快速选择。

**验收标准：**
- 详情页可添加、删除标签。
- 列表页可按标签筛选。
- 标签随录音持久化。

**验证：**
- 添加标签、刷新、筛选、删除标签。

**依赖：** Task 7 可并行。

**预计范围：** 中。

#### Task 9：批量操作

**说明：** 列表支持多选，批量转写、批量摘要、批量删除；批量任务遵守并发限制。

**验收标准：**
- 可多选录音并执行批量转写。
- 批量摘要只对已有转写的录音启用。
- 批量删除有二次确认，并明确删除范围。

**验证：**
- 选择 3 条录音批量转写，任务按队列执行。
- 混合状态录音时按钮可用性正确。

**依赖：** Task 2、Task 8。

**预计范围：** 中。

### Checkpoint C：资料管理验收

- 50+ 条录音仍能搜索、筛选、批量操作。
- 批量任务不会绕过并发限制。

### Phase 3：输出和维护

#### Task 10：导出格式扩展

**说明：** 增加 JSON、SRT、DOCX 导出；现有 MD/TXT 保持兼容。

**验收标准：**
- 转写可导出 JSON 和 SRT。
- 摘要和转写可导出 DOCX。
- 文件名仍沿用安全命名规则。

**验证：**
- 导出文件可打开，中文内容和时间戳正确。

**依赖：** Task 6。

**预计范围：** 中。

#### Task 11：结构化日志和健康检查增强

**说明：** 后端统一 logging，记录任务生命周期、外部命令、LLM 请求摘要、异常栈；健康页显示最近错误和关键配置状态。

**验收标准：**
- 日志写入 `logs/`，支持按大小或日期轮转。
- 静默吞错位置改为记录 warning。
- 健康检查能看到最近错误摘要。

**验证：**
- 人为触发删除文件失败、ffmpeg 失败、LLM 失败，日志可定位。

**依赖：** Task 3。

**预计范围：** 中。

#### Task 12：最小测试集

**说明：** 为任务恢复、并发、搜索、标签、导出和设置写最小自动化测试；前端至少覆盖纯函数和 API client。

**验收标准：**
- 后端有 pytest 最小集。
- 前端可执行 TypeScript build，并补充轻量测试工具后覆盖关键纯逻辑。
- README 记录测试命令。

**验证：**
- 后端测试通过。
- 前端构建通过。

**依赖：** 全阶段滚动补充。

**预计范围：** 中。

### Checkpoint D：3.0 发布验收

- 任务重启恢复、取消、重试、并发限制全部可用。
- 播放、时间轴、高亮、编辑闭环可用。
- 搜索、标签、批量操作可用。
- 导出格式覆盖 MD/TXT/JSON/SRT/DOCX。
- README、CHANGELOG、故障排查文档同步。

## 5. 建议里暂缓的项目

| 项目 | 暂缓原因 | 建议进入 |
| --- | --- | --- |
| WebSocket/SSE | 任务可靠性优先；轮询目前能支撑本地单机使用。 | 3.1 |
| Tailwind/shadcn 迁移 | UI 栈迁移会扩大改动面，不直接提升录音处理能力。 | 3.2 |
| 完整路由系统 | 有体验价值，但低于播放、编辑、搜索。 | 3.1 |
| Alembic | 当前 SQLite 手写迁移仍可控；先补 schema version 和测试。 | 3.1/3.2 |
| 默认说话人分离 | CPU 成本高，先做兼容和实验开关。 | 3.1 |
| i18n | 当前目标用户和文案是中文优先。 | 后续国际版 |

## 6. 风险和应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 任务取消无法强杀正在运行的 FunASR/ffmpeg | 取消体验不完整 | 先实现阶段间取消和 ffmpeg 进程超时；ASR 后续可迁移独立 worker 进程。 |
| Range 播放接口暴露本地文件 | 安全风险 | 只允许读取数据库登记的录音路径，并校验路径归属。 |
| 编辑后的转写与原始 ASR JSON 不一致 | 数据混乱 | 增加 `edited_at` / `is_edited`，保存时同步数据库和 JSON，并保留导出以数据库为准。 |
| 批量任务造成 CPU 占满 | 机器卡顿 | 批量任务必须走队列，并默认 ASR 并发为 1。 |
| 搜索性能随数据增长下降 | 列表变慢 | 第一版用 SQLite LIKE；数据量增大后再引入 FTS5。 |

## 7. 推荐实施顺序

1. Task 1-3：任务可靠性。
2. Task 4-6：播放和校对闭环。
3. Task 7-9：搜索、标签、批量操作。
4. Task 10-12：导出、日志、测试和文档。

这个顺序的好处是每个阶段都能交付一个可用增量：先不丢任务，再能听和改，再能管理大量资料，最后把输出和维护补齐。
